## Roles: Codex builds, Claude supports

Judges score how well we use **OpenAI Codex**, and we submit the session ID of the Codex thread where most of the build happened.

- **Codex** builds the features, mostly in each developer's main thread (listed in `docs/codex-sessions.md`).
- **Claude Code** plans, writes Codex prompts, reviews, debugs when Codex is stuck, makes small fixes, writes tests, docs, the README, and the demo and Devpost text. It builds features only when a developer explicitly asks.

## Claude: Codex prompts first

For **every** build request, Claude's first output is the Codex prompt(s), before any code, review or discussion.

1. Split the work by track (`docs/architecture.md`).
2. Write **one ready-to-paste prompt per affected track**, labeled with the track and its owner. If only one track is affected, say the other is unaffected.
3. Only then add anything else (risks, open questions, review notes), briefly.

Writing prompts (Codex quota is limited, so every prompt must be worth it):
- Intent-based, not step-by-step: goal, context, constraints, definition of done.
- Name the track and the **only folders it may touch**.
- Point to files and docs instead of pasting them.
- Batch related work into one prompt; avoid small back-and-forth tasks.
- Ask Codex to test its work, update the relevant doc, and commit and push following the Git rules below.
- One code block per prompt.

## Codex: taking a task

- Read the docs the prompt points to before writing code.
- Stay inside the folders of the track named in the prompt. If the task needs another track or a contract change, stop and say so instead of doing it.
- Finish with: tests passing, relevant doc updated, committed and pushed.

## Parallel work

Two developers work at the same time, each with their own Codex and Claude Code, each owning one track.

- Tracks, their folders and the shared event contract are defined in `docs/architecture.md`. Owners are in `docs/codex-sessions.md`.
- Tracks talk **only** through the shared contract. Contract changes come **first**: agree, commit, then build against it. Mock the other side until it's ready.
- Flag every contract change to both developers and in the commit body.
- If a task doesn't fit one track, propose the split explicitly before starting.

## Git

- `git pull --rebase` before starting work and before every push.
- Commit and push small and often: after every working unit, not at the end of the day.
- Never force-push `main` or rewrite shared history.
- Merge conflict in code you didn't write: stop, show it, and ask. Don't resolve it blindly.
- When a decision changes (scope, architecture, conventions), update the relevant doc in the same commit.
- Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`); subject imperative, lowercase, under ~60 characters, no trailing period. Example: `feat: mask detected api keys before broadcast`.
- A short body only when the *why* isn't obvious. One logical change per commit.
- **No co-author or "generated by" trailers** in commits or PRs.

## Quality bar

- **Don't add features that weren't asked for.** Suggest them in one line instead.
- Reliability over breadth.
- Run and test before committing; never commit a broken build.
- Small focused modules, clear names, no dead or commented-out code, no premature abstraction.
- Secrets only in `.env`, never committed.
- Minimal dependencies; justify new ones.
- Stack-specific conventions: `docs/architecture.md`.
